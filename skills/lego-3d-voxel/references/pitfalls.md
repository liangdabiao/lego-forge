# 踩坑复盘：现象 → 根因 → 为什么直觉是错的

按"你会先看到什么"排序。每条都真的踩过，代价是以小时计的返工。

---

## 0. 最容易犯的两个方向性错误

### 0.1 用照片取色
用户给了照片，就顺手从照片上取颜色（采样像素 → 量化色板）。
**结果**：颜色脏、明暗当成固有色、阴影区整片发黑，模型看着像旧木头。
而且照片有透视，正面取到的颜色和侧面不是同一套，拼出来斑驳。

**根因**：照片的颜色 = 材质 × 光照。3D 模型的贴图才是材质本身。
**规矩**：只要用户给了 3D 模型，几何和颜色**都只从模型来**。照片只用来核对朝向和轮廓。

### 0.2 看着渲染图"想象"形状
没有真切片，而是"看图 → 觉得这里应该有块砖 → 手写坐标"。人眼对体素的判断极不可靠，
尤其是深度方向：正视图看着对，一转到侧面就是一张纸。

**根因**：中间少了"真实几何"这一层。**规矩**：形状必须由切片数据驱动，
不允许手写任何"我觉得这里应该有"的格子。

## 1. 几乎全白 / 只有零星颜色（196,508 / 230,783 格变成 White）

**现象**：渲染出来白花花一片，只有边缘有一点颜色。

**根因**：取色退路里写了

```python
rgb = (tbl[:, :3] * tbl[:, 3:4]).sum(0) / tot   # 错
```

`tbl[:, :3]` 本来就是各样本 RGB 的累加和，再乘样本数 = **平方放大**，得到的值上十万，
量化时全部落到离色板最远的那个极端（White）。

**正确写法**：

```python
rgb = tbl[:, :3].sum(0) / tot
```

**教训**：颜色/统计类 bug 的表现往往是"整体一个颜色"，而不是"某些格子错"。
看到大面积单一色，第一反应查数值量级，不要查几何。

---

## 2. 每格颜色像是在读"对面那一侧"

**现象**：模型轮廓是对的，但颜色整体错位、前后颠倒，像贴图被镜像。

**根因**：方向数组和编码顺序不一致。

```python
NB    = [(-1,0,0), (1,0,0), ...]        # 写成 -X 在前
binid = ax * 2 + (sgn < 0)              # 编码是 0:+X 1:-X
```

于是 bin 0 存的是 +X 面的样本，却按 -X 去取 → 每格读到背面颜色。

**修法**：`NB` 和 `binid` 同一份注释、同一行顺序，改一个必须改另一个。
最好在代码里写死注释 `# 0:+X 1:-X 2:+Y 3:-Y 4:+Z 5:-Z`。

**为什么难发现**：错位后的结果"看起来仍然是那个模型"，只是颜色怪。很容易误判成"模型贴图有问题"
或"造型不对"，从而在错误方向上改很多轮。

## 3. 成品是一根根垂直柱子，手下面/胳膊之间被填死

**现象**：轮廓大体像，但所有悬垂下方都是实心的，侧面看像几十根柱子捆在一起。

**根因**：内外判定用了"每列取 min..max 填满"。

```python
for a, d in columns:
    for b in range(min_b[a,d], max_b[a,d] + 1):
        solid.add((a, b, d))     # 错
```

人像的列里，min 是"裙摆最低点"、max 是"抬手最高点"，中间全填 → 手臂与身体之间的空腔、
手下方全部变实体。

**为什么球测试没暴露**：球是**凸的**，任何一列的 min..max 恰好就是球体本身，这个 bug 在凸体上
根本不生效。所以球测试只能证明"链路通"，不能证明"空腔对"——两者都要看。

**修法**：三维洪泛（见 `pipeline.md` 第 6 节）。判定标准要从外部空气出发，而不是从某一列出发。

## 4. 只剩一层皮，内部全空

**现象**：件数骤降到原来的几分之一，剖开看是空心壳。

**根因**：直接拿单层外壳 `Ssurf` 去洪泛。三角面之间在体素化后有缝，外部空气顺着缝漏进内部，
于是"内部"也被判成外部，`inside` 为空。

**修法**：洪泛前先把壳 `dilate` 两圈封缝，洪泛后再 `erode` 两圈收回来。

**注意**：只 dilate 不 erode，模型会胖两圈，而且表面格被判成"六面都不朝外"，颜色全丢。
两个操作必须成对。

## 5. 眉眼糊成一片 / 脸上一坨深色（取色策略改了三次）

**现象**：眼睛、眉毛、胡子连成一整块，细节全丢。

这条最容易反复走错，因为"糊"有两种完全不同的原因，而三种取色策略各自能治其中一种：

| 策略 | 结果 | 什么时候该用 |
|---|---|---|
| 平均 RGB | 边界混成中间色，脸红一块暗一块 | 从不用 |
| 众数 | 倾斜面（鼻梁、眉骨）三角面更密，票数压倒平面 → 糊成一团 | 从不用 |
| 离格中心最近的采样点 | 平坦大面很锐利，**细特征整条消失**（格中心常落在背景色上） | 只用来理解"为什么会丢"，不当前默认 |
| **面积加权（现在的默认）** ✅ | 每格显示"覆盖面积最大的那种材料"，锐利且不丢细特征 | 默认 |

**所以**：先确认是"取色糊"还是"层数不够"，两者症状像但修法相反——
加层数能治分辨率，治不了取色；换成面积加权能治取色，治不了分辨率。

**为什么最终没停在"最近点"**：它让财神闭着的笑眼（1.8 层高的一条黑弧线）整条消失——
格中心经常落在弧线旁边的肤色上。面积加权把"这条线在这一格里占多少面积"算进去，才留得住。

**补充**：换成面积加权后如果还糊，就是层数不够（96 → 128），不是取色问题。

## 6. 分辨率不够，整体像色块拼贴

**现象**：轮廓大致对，但五官、衣褶、手指全无，用户判定"根本没切开模型"。

**根因**：层数太少（36 层做 0.9 m 高的坐像）。人像要到 **128 层**。

**尺度换算**：128 层 ≈ 7.8 mm 一层，已经接近真实砖（9.6 mm）的物理上限。
再往上加不会更清楚，只是更贵、更难拼——192 层实测和 128 层的五官清晰度没有区别。

## 6b. 眼睛不见了（最隐蔽的一个）

**现象**：眉毛、胡子都在，唯独眼睛完全没有；把层数从 96 提到 192 也没有。

**查法**（用户要求"底层检查"，这一套查法值得记住）：
1. 把贴图按正投影渲成一张大图（`tex_big.png`），量出眼睛在哪一层、有多厚 → 眼睛在层 72~73，
   厚约 1.8 层，确实存在。
2. 把贴图里的"暗像素"按格子投影，得到「每格暗像素占比」地图 → 眼睛那几格 >50% 是暗的。
3. 再把体素数据按 (列,层) 打 ASCII，对比"期望是暗"和"实际颜色" → 实际是肤色 **0 个黑格**。
4. 最后打**某一列的深度剖面**（同 (列,层) 从远到近逐格列颜色）→ 真相：黑在 z=42、43，
   而 z=44、45 还有两格肤色挡在它前面。
5. **排除误判**：先 `--denoise 0` 重跑一遍。眼睛照样没有 → 不是去噪的锅，是几何和取色两处都错。
   这一步很重要：3×3×3 去噪确实会削 1 格宽的线，很容易被当成唯一元凶而放过真因。

**两个同时存在的根因**：
1. **凹槽被回填**。眼睛是刻在脸上的一道浅槽（槽口 1~2 格宽）。洪泛前为了不漏气要把壳 `dilate(2)`，
   这一步同时把槽口封死 → 空气进不去 → 槽被判成"内部" → 填上实体 → 眼睛被埋掉。
   **修法**：反填（`carve`）——被采样的面朝外那一格必须是空的，见 `pipeline.md` 6b。
2. **细线被面积投票吃掉**。就算槽没被填，1 格高的黑线也会输给周围肤色。
   **修法**：暗细节保底 `--darkdetail`，见 `pipeline.md` 5b。

两条**都必要**：只修几何（挖开槽）眼睛还是不显色，只修颜色（暗保底）槽里仍被实体填着。

**遗留（未解决，别在交付时说"修好了"）**：财神这份扫描件上，carve + `--darkdetail 0.32` 都开了，
128 层渲染出来眉下仍直接是胡子，眼睛没成对出现。已排除的：层数（192 层同样没有）、去噪（关掉同样没有）、
UV 翻转（贴图投影位置正确）。下一步要查的是「眼睛那两格在最终 S 里到底是不是表面格」——
用 `scripts/probe.py --profile 列,层` 打深度剖面，看黑格前面还有没有别的格挡着。

**教训**：不要用"参数都开上了"当验收。验收只有一条——**凑近看渲染图，眼睛在不在**。
我曾在没做这一步的情况下宣布修好，随后被 ASCII 色图和渲染图同时推翻。

## 7. 零件报 "not connected"（已知未完全解决）

**现象**：`lego build` 报几百处 `is not connected to the rest of the set`，
典型是底部 course 的 1×1 / 1×12（`y 0`，x/z 在边缘）。
实测：96 层 266 处，**128 层 503 处**——层数越高，薄边越多，孤岛越多。

**机制**：
- 同色相邻格会被打包成一块更大的砖（横向连接）；
- **不同色**的相邻格在同一 course 里**不连接**，只能靠竖向 stud 连到下层；
- 所以某个格如果 (a) 下方没有格，(b) 左右邻居颜色不同（各自独立）→ 它就是一坨孤岛。

**已定位的原因**：最底层那些"比上一层多出一圈"的边缘格（裙摆/底座外沿）。
它们上方没有砖压着，横向又因为换色断开。

**可选修法（按代价排序）**：
1. 让上一层外扩一格（倒角裙边），把最外层压住 —— 改轮廓最小，但会略微改变外形；
2. 在断连格下方补一格同色（只补 1 格，不是补柱）—— 简单，但底部会长出一层"裙边"；
3. 把断连格改成邻格颜色，让打包器把它们并成一块 —— 颜色会有轻微变化，但外形完全不变；
4. 接受并在交付说明里写明"这几块需要胶水/展示底座"。**不推荐**，用户要的是"能拼"。

**必须做到的验收**：`lego build` 报告 **0 errors**。几百个错不是"差不多"，是"拼不起来"。

## 8. 流程上的坑

- **不要自己加"智能修补"**：曾写过一个 patched 版本，自动补立柱 + 剪孤立格 + 改色。
  补柱把空腔焊死（回到第 3 条的症状），剪格子切出新孤立件，改色把贴图分区糊掉。
  修补要写也必须写在 `vox.py` 里、并且逐条有据可查，不能在 `build.mjs` 里"顺手处理"。
- **一次只改一个假设**：颜色错和几何错同时改，会分不清是哪一处修好了。
  先用三视图/单层切片验证几何，再验证颜色。
- **每版都先给用户看渲染图**：造型/配色这类判断属于用户，不属于我。自己连做三版再交付，
  大概率三版方向都错。
